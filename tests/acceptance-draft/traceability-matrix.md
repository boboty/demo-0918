## 6. 覆盖强度说明（本线主动标注的弱点）

矩阵不仅记录"覆盖了"，也要记录"覆盖得有多硬"。

1. **PD-12.3 以负向断言为主。** AC-11～AC-16、AC-20 主要规定"不能混口径"，
   而对"统一口径后确实可比"的正向证明偏弱（仅有 AC-12 的单位统一与 AC-30 的并列展示）。
   建议在真实数据集上补一个端到端比较案例。
2. **PD-12.6 以负向断言为主。** 该条要求的是"AI 不得越过人工"，
   天然适合用负向断言证明；但缺少一个"研究员确认后草案**正常转为**正式判断"的正例，
   否则无法区分"系统尊重人工"与"系统根本不支持确认"。
3. **WOW2 的验证依赖数据模型能否承载。** AC-32/AC-33/AC-34 要求前提带来源类型与三态结果，
   而当前 P01 数据模型对此承载不足，详见 §7。
4. **"不存在综合评分"属弱验证。** AC-34 以"界面上不存在评分"判定，
   需要明确判定方法（字段级？文案级？），否则容易被绕过。

## 7. 与 P01 数据模型的承载性核对（独立验收发现）

B 线在只依据 `docs/02-data-model.md` 设计案例时，发现以下场景**当前数据模型难以承载**。
此处只记录，不修改冻结资产。

| # | 问题 | 涉及案例 | 严重度 |
| --- | --- | --- | --- |
| G1 | **情报收件箱无承载实体。** `Evidence` 必须提供 `target_type` + `target_id` 且只能指向已存在的 Fact/ProjectEvent/Metric。刚进入、尚未对齐或无法归属的情报无处存放。 | AC-04、AC-01、AC-38 | 高 |
| G2 | **成立前提没有结构化承载。** `Judgment.premises` 是字符串数组，没有来源、没有来源类型（政策文件/同行披露/项目事实/研究员假设）、没有满足/不满足/未知状态，也没有证据引用。WOW2 的核心要求因此无法落库。 | AC-32、AC-33、AC-34、AC-26 | 高 |
| G3 | **集团对照结果无实体。** 前提与集团事实逐项比对的结果（三态）没有可持久化的结构。 | AC-34、AC-26 | 高 |
| G4 | **"候选对齐"与"被否决的对齐"无实体。** `Project.aliases` 只保存对齐**结果**，没有地方保存未确认的对齐提案，也没有地方保存被研究员否决的提案与理由。 | AC-01、AC-25 | 中 |
| G5 | **人工复核动作无留痕结构。** `human_review_status` 是当前状态而非日志；除 `Judgment.last_reviewed_at` 外，没有记录谁在何时以何理由确认/否决。"维持原判断"这一选择无处落库。 | AC-25、AC-27、AC-37 | 中 |
| G6 | **口径只以自然语言存在。** `Metric.scope_definition` 与 `period` 均为自由文本，`unit` 也是自由字符串。因此"同口径比较"依赖文本解析，GW/MW 换算、阶段一致性都无法由模型本身保证。 | AC-11～AC-16、AC-20、AC-30 | 中 |
| G7 | **组织层级缺少"上市平台"标识。** `organization_type` 只有 group/platform/spv/other，无法区分上市平台与非上市平台，而 AC-14 要求跨层比较时提示层级差异。 | AC-14 | 低 |
| G8 | **项目类型枚举覆盖有限。** `project_type` 只有 independent_storage/co_located_storage/other；现实中"共享储能""独立共享储能""台区储能"等只能落入 other，会丢失 AC-15 所需的区分度。 | AC-15 | 低 |
| G9 | **`Project.region` 为单值自由文本。** 而 AC-02 依赖地区作为消歧依据，同一地区在不同来源中的写法（甲省甲县 / 甲县）不一定可比。 | AC-02 | 低 |
| G10 | **原始口径措辞不在 Metric 上直接可见。** 现只能经 `evidence_ids` → `Evidence.evidence_text` 回溯；AC-16/AC-30 要求界面保留原文措辞，实现上需额外拼装。 | AC-16、AC-30 | 低 |

## 8. 产品定义中难以验证或不自洽之处

| # | 出处 | 问题 |
| --- | --- | --- |
| P1 | 第 3 节 vs 第 4 节 | 第 3 节明确以「中国绿发 Mock 内部项目资料」参与同口径比较；第 4 节又规定不得将虚构的项目、经营数据或内部信息挂在真实企业名下，并给出「使用化名企业完成该部分演示」的解法。两条同时成立时，集团自身到底挂真实名还是化名，需要主控明确。 |
| P2 | 第 10 节 | 商业可行性度量（单条情报处理时间、需人工确认比例、一次专题更新所需人时、新情报到研判更新的周期）是运营指标，黑盒业务验收无法验证，且未给出目标阈值。 |
| P3 | 第 12 节 | 六条标准均以「用户能够……完成一次完整研究」表述，缺少可判定的完成阈值（如对齐正确率、允许的人工确认比例上限）。 |
| P4 | 第 7 节 | 规定了 A/B 级可确认关键状态，但未规定 A 级与 B 级互相矛盾时如何呈现。本套案例按「两者保留、不自动覆盖、进入人工复核」设计，属本线补充约定，需确认。 |
| P5 | 第 6 节 WOW2 | 「不做主观评分」只能以"不存在"验证，属于弱验证，判定方法需明确。 |
| P6 | 第 8 节 | 列出判断的「当前状态」，但未定义状态取值集合与解除条件；P01 给出 active/review_required/superseded/draft，产品定义未说明 review_required 何时解除。 |
| P7 | 第 11 节 | 「MVP 明确不做」清单以"不存在"验证，且边界开放（例如「不做 GIS 选址」的边界在哪）。 |
| P8 | 第 4 节 | 「Mock 数据不得与真实事实混合呈现」缺少可判定的边界：是同一界面、同一视图，还是同一次比较？ |

## 9. 使用方式

- 回答"这个需求靠什么证明"→ 查 §1～§5。
- 评估覆盖是否过硬 → 查 §6。
- 判断某个场景能不能落库 → 查 §7。
- 准备与主控对齐范围 → 查 §8。
