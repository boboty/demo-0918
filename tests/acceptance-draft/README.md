# 独立验收案例草案（B2）

## 这套东西是什么

**基于产品定义的黑盒业务验收草案。**

回答的问题是：

> 即使不知道系统准备怎么实现，它最终必须经得住哪些业务场景？

它冻结的是「**什么叫做对**」，不是「怎么做」。

## 这套东西不是什么

- **不是规则测试。** 不引用、不依赖任何 P02 规则编号（`ER-*` / `PS-*` / `EG-*` / `MN-*` / `JI-*`）。
- **不是自动化测试代码。** 本轮刻意不写 pytest、不写执行器、不写 LLM evaluator、
  不写 Playwright / API / UI 测试。产品代码尚不存在，先冻结判定标准。
- **不是产品设计。** 不定义字段、不定义接口、不定义规则。

## 设计依据（只有这两个）

- `docs/01-product-definition.md`
- `docs/02-data-model.md`

**刻意未阅读**（以保证验收案例的独立性，避免"根据开发规则反向编测试"）：

- `docs/03-business-rules.md`
- `rules/*`
- `tests/fixtures/p02-rule-cases.json`

> 独立性不是口号，是流程约束：如果验收案例参照了规则，它就只能证明"规则被实现了"，
> 无法证明"业务需求被满足了"。

## 案例数量与分布

合计 **38** 个。

| 分组 | 主题 | 数量 | 案例 |
| --- | --- | --- | --- |
| A | 实体识别 | 5 | AC-01～AC-04、AC-38 |
| B | 项目事实与状态 | 6 | AC-05～AC-10 |
| C | 指标与口径 | 6 | AC-11～AC-16 |
| D | 未知与冲突 | 4 | AC-17～AC-20 |
| E | 历史研判 | 4 | AC-21～AC-24 |
| F | 人工责任边界 | 3 | AC-25～AC-27 |
| G | 三个 WOW 端到端验收 | 10 | AC-28～AC-37 |

按性质分布：反例 24 个、边界 8 个、正例 6 个。

按 WOW 标记：WOW1 4 个、WOW2 4 个、WOW3 7 个，合计 15 个。

> 本套案例**以反例和边界为主是有意为之**。这个产品的核心风险不是"做不到"，
> 而是"做得太聪明"——错误合并实体、补造生命周期事件、把不同口径伪装成可比、
> 用 AI 判断覆盖人工判断。验收重点因此放在"明确不能发生什么"。

## 单个案例的结构

每个案例包含以下字段（`acceptance-cases.json` 中为同名键）：

| 字段 | 含义 |
| --- | --- |
| `case_id` | 案例编号 |
| `product_goal_refs` | 对应的产品目标 / MVP 成功标准（`PD-*` 锚点） |
| `scenario` | 业务场景 |
| `input_materials` | 输入资料（含证据级别） |
| `expected_user_sees` | 用户期望看到什么 |
| `must_not_happen` | 明确不能发生什么 |
| `acceptance_definition` | 验收结果定义（可判定的通过标准） |
| `classroom_demo` | 是否适合课堂演示 |
| `case_kind` | `positive` / `counter_example` / `boundary` |
| `wow` | 若属于某个 WOW 专项，标记 `WOW1` / `WOW2` / `WOW3` |

## 数据纪律

- 所有输入资料均为**虚构测试数据**（虚构县名、虚构项目名、虚构企业），
  不指向任何真实企业或项目。
- 真实研究对象只用于 `research/` 资料池，**不写死**进验收案例，
  以保证案例可以长期稳定复用。
- 案例中不出现任何可被误认为真实披露的数字。

### B1 与 B2 的关系

B1 找到的真实复杂情况，可以**转成** B2 的抽象验收场景。例如：

> 真实资料中发现"企业新闻与政府文件中的项目名不一致"
> → 抽象为 AC-01「同一项目在多个来源中名称不同」

但 B2 不写死真实企业名称与真实数字。**可以互相利用，不能互相污染。**

## 追踪锚点

`PD-*` 是本线为产品定义章节建立的追踪锚点，用于回答"这个需求靠哪个案例证明"。

- `PD-2.1`～`PD-2.4`：第 2 节四个核心业务问题
- `PD-5`：MVP 业务主链
- `PD-6-WOW1/2/3`：三个关键演示点
- `PD-7`：证据规则
- `PD-8`：历史研判最小结构
- `PD-9`：产品工作区
- `PD-11`：MVP 明确不做
- `PD-12.1`～`PD-12.6`：第 12 节六条 MVP 成功标准

**它不是 P02 规则编号。** 完整定义见 `acceptance-cases.json` 的
`traceability_anchor_scheme` 字段。
